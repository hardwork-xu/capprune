# 项目描述与证据

[English](../en/RESUME.md) · [主页](../../README_zh.md) · [实测结果](EXPERIMENTS.md)

**CapPrune——使用球冠上界、便于审阅的 CPU 精确余弦索引。** 以下是基于证据的项目描述草稿，描述仓库成果，不证明个人掌握程度、作者经历或生产经验。对应英文条目使用相同范围和数字。

## 简历条目

1. 实现 float64 CPU 余弦 top-k 引擎，包含球面 k-means 分块、连续向量排列、保守球冠上界与确定性原始 ID 并列处理；在七种工作负载上验证有序 ID 与实用 BLAS 扫描一致，覆盖 50,000 向量、128 维场景。几何上界与聚类方法来自已有研究。
2. 在 **Apple M1 Pro、请求单线程 Accelerate 预算、合成聚类 50,000×64 向量、k=10** 条件下，将单查询中位数延迟从 **0.9159 ms 降至 0.0898 ms（10.20×）**，平均仅为 **2.34%** 的向量评分。计时不含建库/加载，基线为 float64 扫描加部分 top-k；无法内省 Accelerate 的实际线程数。
3. 设计关闭剪枝的分块消融并保留不利场景：原始像素 digits、各向同性向量与 k=N 场景的耗时分别为扫描的 **4.40×、1.60×、3.69×**。结合评分计数和准备成本识别分布与复用条件；主场景索引建库 **177.159 ms**，按完整建库成本条件推算约需 **215 次查询**回本。
4. 交付不可变、可重复调用的 Python API、双语 CLI、重建证书的受验证 NPZ 持久化、锁定依赖及关联源码哈希的可复现实验。**5,880 次计时调用**保持有序 ID 一致并满足声明的分数容差，最大绝对误差 **4.44e-16**；**70 项本地自动化测试通过**，完成干净隔离环境的 wheel 安装和离线演示验证。相同的 70 项测试、包构建、基准冒烟及 Docker 构建/运行也已在 [Ubuntu 24.04 GitHub Actions](https://github.com/hardwork-xu/cosine-vector-search/actions/runs/35602650743) 通过。

## 简短项目讲解

**为什么选择。** 我希望研究检索中一个具体矛盾：点积更少不一定搜索更快。精确 CPU 索引可以直观看到剪枝决策、开销和结果一致性，无需依赖模型下载或近似召回率取舍。

**如何实现。** 将向量归一化并进行球面 k-means 分块，把每块连续存储，再计算覆盖全部成员的保守球冠。查询按相应上界排序块，仅当剩余上界严格低于第 k 个实际分数时停止。分数并列时保留原始行 ID 更小的结果。

**关键取舍。** 扁平索引容易审阅，但同时保留原始与重排向量，并承担 Python 遍历及 top-k 合并开销。基线采用连续 BLAS 扫描。索引复用不足时，建库和持久化成本尤其重要。

**最有解释力的实验。** 在有利的 50,000×64 合成工作负载上，scan、blocked、pruned 中位数分别为 0.9159、1.6033、0.0898 ms。单独分块遍历更慢；评分比例降至 2.34% 的剪枝，比单一加速数字更直接地解释了有利结果。

**失败与边界。** 真实 digits 虽有少量剪枝，耗时仍为扫描的 4.40×。高维各向同性球冠没有拒绝任何向量，k=N 又必须返回全部向量。结果覆盖一台 CPU 主机、float64、在线批大小 1，不证明大批量吞吐、真实嵌入收益、GPU 支持或所有后端的形式化浮点正确性。

**后续研究问题。** 能否利用低成本几何/负载诊断选择扫描或剪枝？层次结构或更紧上界在真实嵌入数据上能否抵偿新增开销？这些问题需要新增实现及受控多种子实验，不是当前已经实现的功能。
