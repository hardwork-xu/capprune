# 实验与证据边界

[English](../en/EXPERIMENTS.md) · [主页](../../README_zh.md) · [研究约定](RESEARCH.md)

## 主要发现

在本次 Apple M1 Pro CPU 运行中，球冠剪枝在预先指定的**合成聚类 50,000×64、k=10** 工作负载上，相对连续 float64 扫描取得 **10.20× 单查询中位数加速**，平均仅为 **2.34%** 的向量评分。收益强烈依赖数据分布：**真实 digits 的耗时是扫描的 4.40×**，各向同性 50,000×64 为 **1.60×**，32 向量、k=N 边界场景为 **3.69×**。这些负面结果同样包含在交付证据中。这不是预训练嵌入基准，也不是应用端到端结果。

## 工作负载与公平比较

协议覆盖七个场景，各有 40 条查询、七次重复及三种模式：**7 × 40 × 7 × 3 = 5,880 次计时调用**。每场景每模式有 **280 次计时，但只有 40 条不同查询**，重复运行复用这些查询。它们不是 280 份独立数据，也不是多主机研究。种子为 `20260921 + case_index`；各场景原始记录保存了输入数组哈希。

- 合成聚类场景以随机单位中心加标准差 0.035 的高斯噪声生成：5,000×64（32 个生成/请求簇）、50,000×64（64）、50,000×128（64），以及 k=100 的 50,000×64（64）。其他聚类场景使用 k=10。每个索引运行六轮球面 k-means。空簇可能被移除，实际块数有记录。
- 合成各向同性场景采用独立高斯向量和查询：50,000×64、k=10、64 簇；以及 32×8、k=32、8 簇的边界场景。
- `digits_real` 使用 scikit-learn 1.7.2 自带的 `load_digits` 原始 8×8 像素强度。有种子的排列划出 40 条独立查询和 1,757 条库内向量，k=10，32 簇。没有训练模型或嵌入网络，衡量的是数值检索，不是分类精度或语义相关性。[NOTICE](../../NOTICE_zh.md) 保留数据来源归属。

全部模式使用相同的归一化 float64 向量、查询、k、线程请求与确定性分数/ID top-k 函数。`scan` 是实用的连续 NumPy/BLAS 矩阵向量乘加部分选择，不是用 Python 逐行计算的弱基线。`blocked` 使用同一连续分块布局，不计算上界，遍历全部块，用来区分上界剪枝收益与排列、调度和合并开销。`pruned` 计算上界、排序块，并在文档说明的 float64 保守余量下跳过无法竞争的块。

原始排列为扫描基线保留，连续分块排列支持块遍历，测量时二者存在于同一索引。这是在共享内存预算下比较延迟，不声称剪枝索引比纯扫描实现更省内存。查询矩阵 API 逐条处理，不是大批量 GEMM 基线，也没有比较 Faiss、近似索引或 float32 检索。

## 计时与统计

`perf_counter_ns()` 包围每次 `index.search(query, k, mode=...)`。计时包含输入验证、查询归一化、启用时的上界计算、向量评分、选择/合并与结果分配。数据生成、建库、保存/加载、scan 参考答案及返回结果验证不在查询计时中。建库与序列化成本在下文单独报告。没有 JIT 编译。

每种模式先预热四条查询。每次重复随机排列查询顺序，并对每条查询独立随机排列模式顺序，减少固定顺序偏差。保留全部有效样本。下表中位数与第 25–75 百分位区间描述经验计时分布，不是置信区间。[summary.json](../../results/analysis/summary.json) 还保留每次重复的七个中位数。不作 p95/p99、统计显著性、并发吞吐或服务级别结论。

`first_query_ns` 是在完成建库、序列化、往返查询和 scan 参考计算**之后**的首次计时调用，**不是冷进程启动或冷缓存延迟**。主场景的这三个值分别为 scan 1.1943 ms、blocked 1.6838 ms、pruned 0.1161 ms。实验没有测量解释器启动、首次导入、依赖安装或应用流程。

## 建库、持久化与内存

每个场景的建库、保存和加载均**只测量一次**，显示精度不能理解为延迟分布。建库含归一化、聚类、重排和球冠构建。保存含压缩 NPZ 序列化及文件系统写入；加载含读取、验证和证书重建。主场景还实际需要 177.159 ms 建库、764.400 ms 保存、88.470 ms 加载。这些成本影响复用与启动，不应被查询加速比掩盖。

1 MiB 为 2²⁰ 字节。`index_array_bytes` 是索引保留的 ndarray 载荷总和，包含原始与重排向量，不含 Python 对象、临时数组或 BLAS 分配。`process_rss_after_build_bytes` 为某时刻进程 RSS，含解释器、输入与分配器保留内存。`process_peak_rss_after_bytes` 是**进程累计高水位**，包含先前场景、建库与 I/O。tiny 场景的 577.266 MiB 峰值不是该微型索引的内存需求：其保留索引数组仅占 5,256 字节。这些统计不能识别各查询模式的独立峰值，也不能证明相对扫描节省内存。

## 解释、消融与局限

主有利分布上，blocked 需要 1.6033 ms，scan 为 0.9159 ms，而剪枝降至 0.0898 ms，仅评分 2.34% 的向量。因此，仅靠排列和块遍历无法解释收益，避免多数评分和合并是关键。块消融同时将上界顺序改为存储顺序，因此没有隔离全部顺序/选择交互影响。

各向同性数据仍评分 100% 向量，耗时为扫描约 1.60×：宽球冠没有有效拒绝能力，却留下调度、上界和合并开销。真实 digits 仍评分 84.36% 向量，耗时为扫描 4.40×；小规模集合上有限工作量减少无法抵偿开销。k=N 时需要全部候选，tiny 场景耗时为扫描 3.69×。这些结果否定“普遍加速精确搜索”的主张，并支持在这些已测输入上使用 scan。

k=10 与 k=100 的聚类场景使用不同种子，因此数据不同。它们证明两种工作负载可运行，**不是控制其他变量的单独 k 消融**。跨规模比较同样属于覆盖测试，不是固定其他全部因素的扩展规律。单主机、每场景一个有种子的数据集、40 条查询、请求线程数、float64 和紧密合成聚类限制了推广范围。数值测试验证这些输入满足声明的一致性，不是对全部 IEEE-754/BLAS 边界情况的形式证明。新嵌入数据集、多种子、多簇数、自适应扫描回退和更紧/层次上界属于后续研究，尚未实现。
